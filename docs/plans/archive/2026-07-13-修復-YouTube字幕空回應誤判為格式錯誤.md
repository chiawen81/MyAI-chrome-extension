# 修復：YouTube 字幕來源回空內容，被誤判為「格式無法解析」

> 看板編號：#18　狀態：已完成（2026-07-13 手動驗收通過，收尾歸檔）

## 🔸 User Story

作為使用者，在 YouTube 影片走以下動線開啟雙語字幕：

```
點「譯」 → 選來源字幕（含「英文（自動產生）」） → 「開啟雙語字幕」
```

1. 能成功取得來源字幕並顯示雙語對照字幕；

2. 若字幕真的拿不到，面板要顯示**準確的失敗原因**（來源回空內容），而不是誤導成「YouTube 可能已改版／格式問題」。

### 🔹 1. 根因分析（兩層）

**直接根因：錯誤分類層（已從原始碼確認）**——解析前缺少「空回應／非預期內容」的前置檢查，把「拿不到內容」誤分類成「格式解析失敗」。實際上**格式從未改版，是內容為空**。

`fetchCues()`（subtitle-provider.ts:138–152）的失敗流程：

```
fetch(baseUrl + '&fmt=json3')
  → YouTube 回 HTTP 200，但 body 為空字串（非 4xx）
  → parseJson3('')：JSON.parse('') 拋錯 → 進 catch
  → fallback parseTimedTextXml('')：DOMParser 解析空字串得 parsererror 文件、
    querySelectorAll('text') 為 0
  → 拋出「字幕格式無法解析…YouTube 可能已改版」   ← 誤判點
```

**上游根因：字幕 URL 取得層（Task 3 spike 已實證）**——問題不在格式參數，而在**該 URL 本身已無授權取得內容**（使用者實測：該 baseUrl 無論 `fmt=json3`／`srv3`／不帶 fmt／有無 `variant=gemini`，一律 200 空 body）。

<details>
<summary>展開查看：上游根因的推測依據（pot token／variant=gemini）</summary>

- `baseUrl` 來自「重新 fetch watch 頁 HTML → 抽 `ytInitialPlayerResponse` → `captionTracks[].baseUrl`」（檔頭註解的方案 A）。

- 推測：YouTube 對 timedtext 端點要求 `pot`（proof-of-origin token，BotGuard 產生、由播放器在請求時附加），條件不符時靜默回 200 空 body 而非 4xx；自動產生（ASR）字幕軌受影響最明顯。

- `variant=gemini` 是近期新出現的參數（推測與新的自動字幕管線相關），本模組的取得邏輯未跟上。

- 此推測與 yt-dlp 社群自 2024 起記錄的行為一致，但**須以 spike 實證，不得憑推測實作**。→ 已由 Task 3 spike 實錘（見 §3-C 與附錄）。

</details>

### 🔹 2. 現況 vs 預期

| | 現況 | 預期 |
|---|---|---|
| 空回應處理 | 空字串直接進 json3／XML 解析器，拋「格式無法解析」 | 解析前偵測空／非預期內容，回報「字幕來源回傳空內容」 |
| 格式 fallback | 只有 json3 → XML（同一份 body 換解析器） | json3 空 → 重抓 srv3 → 重抓預設 XML；必要時去除 `variant` 重試 |
| URL 取得 | 重抓 watch 頁 HTML 的 `ytInitialPlayerResponse.baseUrl`，缺 pot | 取得帶有效授權（pot）的字幕 URL |
| 錯誤訊息 | 一律「YouTube 可能已改版」 | 依失敗型態分類（空內容／格式異常／HTTP 錯誤） |

### 🔹 3. 修復方案（三段）

**A. 錯誤分類前置檢查（短期，必做）**

`fetchCues` 取得 body 後先檢查，再決定是否交給解析器：

```
body 為空白字串        → 「字幕來源回傳空內容，可能是 YouTube 暫時擋下此字幕軌，
                          請重新整理頁面再試」
非 { 開頭且非 < 開頭   → 「字幕來源回傳非預期內容」
看起來像 json3／XML    → 才交給對應解析器
                         （保留現有「格式真的變了」的錯誤分支）
```

**B. 格式 fallback 鏈強化（低成本體質提升）**

依序**重新請求**（不是同一份 body 換解析器）：

```
fmt=json3 → fmt=srv3 → 不帶 fmt（XML）
  任一非空 → 解析
  全部為空 → 若 baseUrl 含 variant= 參數，去除後再走一輪
  仍全空   → 拋 A 的「空內容」錯誤
```

註：對本案例影片手測已全空，B 預期救不了它（治本靠 C），但可涵蓋其他「單一格式暫時性回空」的影片。

**C. URL 取得邏輯修正（治本，先 spike 再實作）**

**Spike 結論（2026-07-13）：採路徑 3（InnerTube，ANDROID client）**。過程與數據見附錄，實作要點：

- 架構影響：**不需 main-world 注入、不改 manifest**，全部收在 `subtitle-provider.ts`；InnerTube 僅作為「原始 baseUrl 全空時」的備援，正常路徑不多打請求。

- ANDROID 的 baseUrl **已含 `fmt` 參數**，指定格式必須用 URL API 設定（setSearchParams），字串附加會被伺服器忽略（只認第一個 fmt）。

- track 欄位（`name.runs`／`languageCode`／`kind`）與 watch 頁結構相同，現有 mapper 直接相容；`?key=` 參數可省略（content script 讀不到 ytcfg，此點關鍵）。

<details>
<summary>展開查看：三條候選路徑的評估與 spike 實測證據</summary>

候選路徑（Task 3 實測擇一）：

1. **main world 讀取 live player**：`#movie_player` 的 `getPlayerResponse()` 拿目前 session 的 `captionTracks.baseUrl`（可能與重抓 HTML 的版本不同）。需 main-world 注入＋postMessage 橋接（content script 在隔離世界，這正是現行方案 A 繞開的限制）。

2. **攔截播放器自身的 timedtext 請求**：使用者（或程式）開啟 CC 時播放器會自己發含 pot 的 timedtext 請求，main-world hook fetch/XHR 擷取完整 URL 複用。最可靠（拿到的一定是能用的 URL），但實作面最重。

3. **InnerTube API**（`youtubei/v1/player` 換 client context 取 track）：yt-dlp 做法，不需 main-world 注入，但屬與 YouTube 的軍備競賽，失效週期不可控。

依隔離慣例，無論採哪條，「與 YouTube 內部結構相關」的邏輯仍集中於 `subtitle-provider.ts`（若需 main-world 檔案，新增檔案並於 ARCHITECTURE.md 記錄注入方式與跨世界訊息）。

spike 實測證據：

- 根因實錘：播放器自己的 timedtext 請求帶 `pot` → 200 有內容（CC 正常顯示）；同 URL 去掉 pot → 200 空 body。缺 pot 假說成立。

- 路徑 1 出局：live player 的 baseUrl 與重抓 HTML 的**完全相同**（同樣無 pot），fetch 同樣回空。

- 路徑 2 不必要：路徑 3 已可行且實作輕得多。

- 路徑 3 實證可行：ANDROID／IOS client 拿到的 baseUrl **不需 pot** 即可取得完整字幕內容；WEB client 不回字幕軌、TVHTML5 要登入、MWEB 不可播。

</details>

<summary>展開查看：四輪執行紀錄（路徑盤點 → 換 client → 實作前提 → 端到端驗證）</summary>

**第一輪（路徑盤點）**：

| 路徑 | 做法 | 結果 |
|---|---|---|
| A0 現行 | 重抓 watch 頁 HTML → `ytInitialPlayerResponse.captionTracks[].baseUrl` | 200 空 body（json3／srv3／無 fmt 皆同） |
| C1 live player | `#movie_player.getPlayerResponse()` | baseUrl 參數與 A0 **完全相同**（無 pot），同樣回空 → 出局 |
| C2 攔截 | `page.on('request')` 收 `/api/timedtext` | 攔到的 URL 重放仍空（此輪未攔到帶 pot 的那筆） |
| C3 InnerTube WEB | POST `/youtubei/v1/player`（WEB client） | `captionTracks` 為空陣列 → WEB client 出局 |

**第二輪（回應攔截＋換 client）**：

- `page.on('response')`：播放器開 CC 後自己發的請求**帶 `pot`** → 200、14KB json3，CC 畫面實際顯示字幕（截圖確認）→ **缺 pot 假說實錘**。

- InnerTube 換 client 並 fetch 首軌 baseUrl：ANDROID（20.10.38）→ 200／24KB（srv3 XML）✅；IOS（20.10.4）→ 200／67KB（json3）✅；TVHTML5 → `LOGIN_REQUIRED`；MWEB → `UNPLAYABLE`。ANDROID／IOS 的 baseUrl **不需 pot**。

**第三輪（實作前提）**：不帶 `?key=` 的 InnerTube POST → 200／playability OK／2 軌；track 欄位 `name.runs`＋`languageCode`＋`kind`＋絕對 baseUrl（與 watch 頁結構相同）；ANDROID baseUrl 已含 `fmt` → 需用 URL API set 而非字串附加；watch 頁 HTML 含 `INNERTUBE_API_KEY`（備援用，最終不需要）。

**第四輪（修復後流程端到端驗證）**：把新版 `fetchCues` 邏輯原樣移植到頁面 context 執行，輸入為 A0 的 asr 軌 baseUrl：第一輪 6 個候選（json3／srv3／無 fmt × 原始／去 variant）全部 200 空 → 拋「字幕來源回傳空內容…」→ InnerTube ANDROID 備援 → 新 baseUrl 設 `fmt=json3` → 200／228KB → 解析出 **431 句** cue（首句 `[music]`，含真實對白）✅。

</details>

**InnerTube 請求最小重現**（在 youtube.com 頁面 console 或 content script 執行）：

```js
const res = await fetch('https://www.youtube.com/youtubei/v1/player', {
  method: 'POST',
  headers: { 'content-type': 'application/json' },
  body: JSON.stringify({
    context: { client: { clientName: 'ANDROID', clientVersion: '20.10.38', androidSdkVersion: 30, hl: 'en' } },
    videoId: 'U9DqnBmXqN0',
  }),
  credentials: 'include',
});
const tracks = (await res.json())?.captions?.playerCaptionsTracklistRenderer?.captionTracks;
// tracks[i].baseUrl 以 URL API 設 fmt=json3 後 fetch，應回非空 json3
```

失效時的檢查順序：① clientName/clientVersion 是否仍被接受（playabilityStatus）② captionTracks 是否仍在 `captions.playerCaptionsTracklistRenderer` ③ baseUrl 是否也開始要求 pot。
