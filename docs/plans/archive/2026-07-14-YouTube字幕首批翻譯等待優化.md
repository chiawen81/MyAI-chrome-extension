# YouTube 字幕首批翻譯等待優化（看板 #20）

> 類型：優化（場景四流程）｜狀態：已完成（①＋②採用並通過核心效能 UAT、③不做、④移交 #21——2026-07-14 使用者確認結案）
> 對應看板：docs/任務看板.md #20

<br><br>

## 🔸 User Story

身為 YouTube 雙語字幕的使用者，我想要在開啟字幕後**幾秒內就看到譯文開始出現**，以便確認翻譯正常運作，而不是盯著純原文字幕 15～58 秒、誤以為翻譯失敗。

<br><br>

## 🔸 根因分析

🔹 現況鏈路

```
startSubtitles()（src/content/youtube/index.ts）
  → fetchCues() 下載整軌字幕
  → 掛 overlay（此時只有原文）
  → 查「影片級」整包快取，未命中 →
  → translateAllCues()：for 迴圈【循序】逐批 await
       每批 = youtubeBatchSize 句（預設 40）
       └→ TRANSLATE_BATCH → background：
            逐句查快取 → 未命中切子批（≤30句/3000字）
            → 並行呼叫 API（semaphore，預設並發 3）
            → 【整批全部完成】才回應
  → 批次回應後才渲染該批譯文、送下一批
```

🔹 首批延遲的組成

首批延遲 ＝ LLM 一次翻完 40 句的生成時間（40 句通常被 background 切成 2 個子批並行，實際等的是較慢的那個子批）。句子越長、模型越慢，延遲越大——實測 15～58 秒，變異來自供應商／模型／句長。

後續總時長 ＝ 各批延遲**相加**（循序），一部 400 句的影片要等 10 批接力跑完。

🔹 關鍵事實：批次之間沒有資料依賴

每批的 context 是**前一批最後 2 句「原文」**（`index.ts:339-342`），不是譯文；原文在下載字幕時就全部拿到了。循序執行只是實作選擇，不是正確性需求。

🔹 重要發現：逐句快取早已逐批寫入（影響方向③評估）

background 的 `handleTranslateBatch` 在**每次批次請求完成時**就把新譯文逐句寫入快取（`service-worker.ts:204`）。看板 #20 描述「中途換片全部作廢重來」與現況不符：中途作廢損失的只有 content script 端「影片級整包快取」；重開後批次重跑時 API 全數命中逐句快取，**不重複扣費、回應也快**（只剩訊息往返與 storage 讀取）。FEATURES.md 已知限制其實已記載「逐句快取仍有效」。

<br><br>

## 🔸 方向盤點（效益 × 風險 × 決議）

| # | 方向 | 效益 | 風險／成本 | 決議 |
|---|---|---|---|---|
| ① | 批次並行化（content 端並發池、回來即渲染） | 大：總時長從「各批相加」→「最慢批 × ⌈批數/並發⌉」 | 中低：詳下 | **採用** |
| ② | 首批縮小為 10 句 | 大：首句譯文在單一小批往返內出現（數秒） | 低：多一次 API 往返 | **採用** |
| ③ | 逐批寫入影片級快取 | **重估後低**（見上節：逐句快取已逐批持久化） | 中：要處理部分陣列載入＋續翻缺口邏輯 | **不做** |
| ④ | 從播放位置優先翻譯 | 中（長片跳看情境） | 高：拖動進度條需重排佇列、複雜度高 | **緩做**，看①＋②實測成效再議 |

🔹 ①＋②組合後的預期效果

首批 10 句先回來（數秒）即渲染；其餘批次同時在跑，整體完成時間大約除以並發數。

<details>
<summary>展開：以實測 58 秒的影片試算</summary>

假設該影片 400 句、40 句/批共 10 批、每批約 58 秒、並發 3：

- 現況：首批 58 秒才見譯文，總時長 ≈ 58 × 10 ≈ 580 秒
- 改後：首批 10 句 ≈ 15 秒內見譯文；總時長 ≈ 58 × ⌈10/3⌉ ≈ 232 秒

（實際數字受供應商併發回應速度影響，僅為量級估算。）

</details>

🔹 ① 的風險盤點與對策

- **供應商 rate limit**：並發數已由 SW semaphore 統一限流（`settings.concurrency`，預設 3、可調 1～10），content 端沿用同一設定值做派發池大小，不另立參數；遇 429 屬既有錯誤路徑，使用者可調低並發。
- **完成順序亂序**：`translations` 陣列按索引寫入、overlay 每批 `setData` 重掛，本來就支援亂序漸進渲染，無需改 overlay。
- **進度顯示**：循序的「n / total 句」語意失效，改為**已完成句數計數制**（誰先回來就加誰）。
- **失敗處理**：現況一批失敗即中止後續。並行下改為：任一批失敗 → 停止派發未送出的批次、已完成譯文保留在畫面上、狀態列顯示失敗訊息、**不寫**影片級整包快取（陣列有缺口）。
- **取消（換片／關閉／重開）**：沿用既有 `cancelled` ＋ `runToken` 檢查點——每批 sendMessage 回來先驗代號，失效即丟棄結果，機制不變。
- **不齊發、用池**：不一次把所有批次全丟給 background（每個 TRANSLATE_BATCH 在進 semaphore 前就會做 loadSettings＋逐句 hash 查快取，齊發幾十批徒增瞬時開銷），content 端以 `settings.concurrency` 為上限派發。

## 🔸 Spec

🔹 現況 vs 預期行為

| 面向 | 現況 | 預期 |
|---|---|---|
| 首句譯文出現 | 首批 40 句全翻完（15～58 秒） | 首批縮為 10 句，單一小批往返內出現（目標數秒～10 秒級） |
| 批次執行 | 循序，一批完才送下一批 | 並發池（上限＝`settings.concurrency`），回來即渲染 |
| 進度顯示 | 「翻譯中… n / total 句」依批次順序 | 已完成句數計數（亂序累加），progress bar 同步 |
| 批次失敗 | 中止後續、顯示錯誤 | 停止派發新批、保留已完成譯文、顯示錯誤、不寫整包快取 |
| 影片級快取 | 全部完成才寫 | 不變（全部成功才寫） |
| 逐句快取 | background 每批完成即寫 | 不變 |
| 批次 context | 前一批最後 2 句原文 | 不變（原文事前已備齊，並行不受影響） |

🔹 邊界條件

- 字幕句數 ≤ 首批大小：單批送完即結束，行為同現況。
- 首批大小固定 10 句（8～12 的中間值），**不新增設定欄位**；後續批維持 `youtubeBatchSize`（含既有 `Math.max(5, …)` 下限）。
- 快取命中路徑（影片級整包）不經過 `translateAllCues`，不受本次改動影響。
- 換片／關閉／關了立刻重開：各批回應處的 `cancelled`／`runToken` 檢查沿用，失效批次結果直接丟棄。

🔹 錯誤處理

- 任一批 `response.ok === false` 或 sendMessage throw：記下錯誤、不再派發新批；等在途批次收尾（結果仍渲染），最後狀態列顯示 `翻譯失敗：<訊息>`、progress 隱藏。
- 全部成功才 `cacheSetMany` 寫影片級整包快取＋顯示「翻譯完成。」。

🔹 驗收標準（手動，chrome://extensions 載入後於 YouTube 實測）

- [x] 開啟雙語字幕後，首句譯文於單一小批往返時間內出現（UAT 約 10 秒；先前同類影片為 15～58 秒）
- [x] 整部影片翻譯總時長明顯下降（UAT：25 分鐘影片、280 句，約 1 分 40 秒翻完）
- [ ] 譯文亂序漸進補上，無錯位（抽查前中後段譯文與原文對應）
- [ ] 進度條與「已完成 n / total 句」隨批次完成累加，最終達 100%
- [ ] 翻譯完成後關閉再開啟 → 「已從快取載入譯文。」（影片級快取行為不變）
- [ ] 翻譯中途換片 → 舊譯文不殘留、無報錯；換回原片重開 → 快速完成（逐句快取命中）
- [ ] 翻譯中途關閉字幕再立刻開啟 → 無新舊流程互相覆蓋（runToken 防護仍有效）
- [ ] 模擬失敗（如暫時填錯 API key）→ 已完成譯文保留、狀態顯示失敗、重試可恢復

🔹 2026-07-14：首批改為單獨先送（首輪驗收回饋）

- **變更**：首批不進並發池——單獨先送、完成渲染後其餘批次才開池並行（`translateAllCues` 拆出 `runBatch`，池從 batch 1 起跑）。
- **原因**：首輪驗收發現首批延遲不穩、有時比舊版更久。研判為首批與兩個 40 句大批同時送出，供應商端限流／排隊拖慢了小首批；單獨先跑讓它獨占容量，代價僅總時長多一小批的串行往返。
- **驗收補充判讀**：觀感上的「譯文出現」是播放位置那句有譯文；若狀態列句數在漲但畫面仍原文，屬播放位置已超過已翻範圍（見看板 #21，屬方向④範疇，本計畫不處理）。
