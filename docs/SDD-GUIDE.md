# SDD 操作指南（docs/SDD-GUIDE.md）

> **閱讀對象**：開發者本人（這份文件給人看，不是給 AI 執行的指令）
> **放置位置**：專案 `docs/SDD-GUIDE.md`
> **搭配前提**：CLAUDE.md 已含「計畫歸檔流程」與「文件同步檢查」兩條關鍵規則

## 🔸 本文件的使用方式（先讀這段）

| 內容類型 | 怎麼用 |
|---|---|
| 流程圖、判斷準則 | 開發者自己看，決定當下走哪個場景 |
| `📋 指令範本` 程式碼區塊 | **複製 → 替換 `{{挖空}}` → 貼到 VSCode 的 Claude Code 對話中執行** |
| 第 7 節 slash command 檔案 | 一次性建置：把該節的建置指令貼給 Claude Code 執行，之後日常改用 `/指令` 呼叫 |

## 🔸 0. 場景分派總覽（任務進來先走這張圖）

```
                     ┌─ 有任務 ─┐
                     ▼
          這是修 bug 還是做功能？
           │                  │
         [bug]              [功能]
           │                  │
    只動 1 個檔案、        現在要動工，
    不改變對外行為？       還是先討論？
     │          │          │         │
   [是]       [否]      [先討論]   [動工]
     │          │          │         │
  場景三      場景四      場景二    場景一
  直接修     Fix 計畫    Plan-only  完整 SDD
                                     │
                          開發中途需求變了？→ 場景五
```

**判斷準則備忘**
- 「對外行為」= 使用者可感知的行為（翻譯結果、UI、快捷鍵、儲存格式）。改註解、改 log、修 typo 都算「不改變」。
- 拿不準時一律當場景四處理（寧可多一份輕量計畫文件，不要少）。

## 🔸 1. 場景一：開發新功能（完整 SDD 流程）

```
產生計畫 → 人工審閱 Spec →(不滿意→改計畫，循環)→ 依計畫實作
   │                                                  │
   └── 產出 docs/plans/YYYY-MM-DD-<feature>.md        ▼
                                            逐 Task 實作＋勾選
                                                      │
                                                      ▼
                                     手動驗收（chrome://extensions）
                                                      │
                                                      ▼
                                        文件同步＋計畫歸檔（場景六）
```

**📋 指令範本 1-A：產生計畫（只規劃、不寫碼）**

```
請為以下功能建立開發計畫，只產出計畫文件，禁止寫任何程式碼。

功能名稱：{{功能名稱}}
需求描述：{{一段話描述使用者要達成什麼}}
規格書對應章節：REQUIREMENTS.md {{章節編號，無則填「無，為新需求」}}

輸出至 docs/plans/{{今天日期 YYYY-MM-DD}}-{{feature-slug}}.md，結構：
1. User Story（身為…我想要…以便…）
2. Spec（具體行為、邊界條件、錯誤處理、驗收標準——驗收標準必須可勾選）
3. Tasks（拆成可獨立完成的步驟，每步標註影響的檔案）

產出後停下等我審閱，不要繼續實作。
```

**📋 指令範本 1-B：依計畫實作**

```
請依 docs/plans/{{計畫檔名}}.md 實作。要求：
1. 依 Tasks 順序逐項完成，每完成一項在計畫文件中勾選
2. 每完成一個可測試的模組即停下，提示我手動載入測試
3. 過程中若發現 Spec 有缺漏，先停下與我確認，不要自行擴充範圍
```

## 🔸 2. 場景二：只討論、先不開發（Plan-only）

用途：新點子還不成熟、要來回討論規格時。討論的產出物 = 計畫文件草稿，之後隨時可接回場景一的 1-B。

**📋 指令範本 2-A**

```
我想討論一個新功能的可行性與規格，此階段禁止寫程式碼、禁止修改既有檔案。

初步想法：{{描述想法，可以很粗糙}}
我的疑慮：{{技術可行性／與現有架構的衝突／成本，擇要填}}

請：
1. 先閱讀 ARCHITECTURE.md 與 REQUIREMENTS.md，評估此想法與現有架構的相容性
2. 提出 2~3 個實作方向（各一段），標出你推薦的一個＋理由
3. 等我選定方向後，再產出計畫文件草稿至 docs/plans/（標註 status: draft）
```

## 🔸 3. 場景三：Debug — 小修（單檔、不改行為）

不開計畫文件，直接修，但 CHANGELOG 必記。

**📋 指令範本 3-A**

```
Bug 小修（單一檔案、不改變對外行為）：

現象：{{看到什麼錯誤／貼上錯誤訊息}}
重現步驟：{{怎麼觸發}}
懷疑位置：{{檔案路徑，不確定可填「請先定位」}}

要求：
1. 修復前先說明根因，經我確認後再改
2. 修改範圍若超出單一檔案或會改變對外行為，停下改走 Fix 計畫流程
3. 完成後在 CHANGELOG.md 補一行紀錄
```

## 🔸 4. 場景四：Debug — 大修（跨模組或改變行為）

**📋 指令範本 4-A**

```
Bug 修復（需要計畫）：

現況行為：{{目前發生什麼}}
預期行為：{{正確應該是什麼}}
重現步驟：{{步驟}}
影響範圍推測：{{已知會動到的模組，不確定可留白}}

請先建立 docs/plans/{{今天日期}}-fix-{{問題-slug}}.md：
1. Spec 段寫「根因分析 → 現況 vs 預期行為 → 修復方案」
2. Tasks 拆步驟，標註影響檔案與是否改變對外行為
產出後停下等我確認，再依計畫修復。
完成後同步：CHANGELOG.md 一律更新；若對外行為改變，同步 FEATURES.md。
```

## 🔸 5. 場景五：開發中途需求變更

原則：**改計畫文件，不要只在對話裡口頭改**（口頭變更在 session 結束後消失，計畫文件才是跨 session 的合約）。

**📋 指令範本 5-A**

```
需求變更。請先更新 docs/plans/{{計畫檔名}}.md 再繼續實作：

變更內容：{{原本是什麼 → 改成什麼}}
變更原因：{{一句話}}

要求：
1. 更新 Spec 與受影響的 Tasks（已完成但被此變更作廢的 Task，標註 [作廢] 而非刪除）
2. 在計畫文件底部加一節「變更紀錄」記錄本次變更
3. 更新完停下讓我確認，再繼續依新版計畫實作
```

## 🔸 6. 場景六：文件同步與歸檔（功能完成時）

CLAUDE.md 的同步規則會讓 Claude Code 在任務尾聲自動做，但**功能完成點**建議用明確指令收尾一次，避免遺漏：

**📋 指令範本 6-A：功能完成收尾**

```
{{功能名稱}} 已通過手動驗收，請執行完成收尾：
1. docs/plans/{{計畫檔名}}.md 移至 docs/plans/archive/
2. FEATURES.md：更新此功能狀態與行為描述（含已知限制）
3. CHANGELOG.md：補上本次變更
4. 檢查本次開發是否新增 message／storage key／Provider，有則同步 ARCHITECTURE.md
5. 列出你這次同步了哪些文件讓我核對
```

**📋 指令範本 6-B：脫鉤稽核（覺得文件不可信時使用）**

```
請執行文件與程式碼的脫鉤稽核：
1. 逐一核對 ARCHITECTURE.md 的 message 表／storage 結構／目錄結構是否與現有程式碼一致
2. 核對 FEATURES.md 各功能描述與實際行為是否一致
3. 只列出不一致清單與修正建議，經我確認後再修改文件
```

## 🔸 7. 自動化評估（slash command / skill / hook）

| 場景 | 建議形式 | 理由 |
|---|---|---|
| 1-A 產生計畫 | **slash command** `/sdd-plan` | 高頻、結構固定、只需填空 |
| 3-A 小修 | **slash command** `/sdd-fix` | 同上 |
| 6-A 完成收尾 | **slash command** `/sdd-done` | 步驟固定，最容易被遺忘，自動化價值最高 |
| 文件同步提醒 | **hook**（第二階段再做） | Stop hook 可在每次任務結束時檢查提醒，但 hook 設定語法版本差異大 ⚠️ 需自行驗證當前 Claude Code hooks 文件 |
| 整套 SDD 流程 | **skill：現階段不建議** | skill 適合封裝跨專案的複雜能力；單人單專案下 CLAUDE.md 規則＋slash commands 已覆蓋，再加 skill 只是多一層維護 |
| 多視窗並行時的段落收尾 commit | **skill** `/commit-session`（✅ 已建置） | 需要盤點「本對話改過哪些檔案」並判斷 diff hunk 歸屬，靠模型推理而非固定填空範本，slash command 做不到 |

判斷原則：**高頻＋固定結構 → slash command；需要「強制執行」而非「主動記得」→ hook；跨專案可攜的能力包 → skill**。

### 7.1 已建置 skill：/commit-session

**用途**：多個 Claude Code 視窗同時在本專案工作時，只把「當前視窗（本次對話）」造成的檔案異動 commit，不夾帶其他視窗未收尾的修改。

**觸發方式**（三者等價）：
- 輸入 `/commit-session`
- 說「commit 這個視窗的異動」
- 說「到一個段落了幫我 commit」

**行為摘要**：
1. 盤點本對話中實際改動的檔案（不用 git status 反推，避免撈到其他視窗的檔案）
2. 同一檔案被多視窗改到時，以「HEAD 版重套本對話修改 → 寫進 index」做選擇性 staging，工作目錄不動
3. 依 COMMIT-CONVENTION.md 撰寫訊息後 commit（不用 `-a`）
4. commit 後回報：hash＋檔案清單＋**token 用量與 Claude API 等值費用**（分「本段：自上次成功 commit 後」與「視窗累計」兩組；同視窗第二次執行時只有新增用量算進本段）

**注意事項**：
- hunk 歸屬無法確定、或兩視窗改到同一行時，會停下來問你，不會猜
- 對話經過 context 壓縮時檔案清單可能有遺漏，回報中會註明
- 費用是「若走 API 計價」的等值估算（訂閱方案實際不按 token 扣費）；統計含 system prompt 與 cache 用量，token 數看起來大是正常的，占大宗的 cache 讀取單價僅為 input 的 1/10
- 定義檔：`.claude/skills/commit-session/SKILL.md`＋`count-session-tokens.py`（定價表寫死在腳本內，新模型需手動更新）

**一次性建置指令**（貼給 Claude Code 執行一次）：

```
請建立三個 slash commands 於 .claude/commands/：

1. sdd-plan.md — 內容為本專案 docs/SDD-GUIDE.md 場景一範本 1-A，
   將挖空欄位改為 $ARGUMENTS 承接（用法：/sdd-plan 功能名稱＋一句需求）
2. sdd-fix.md — 對應範本 3-A，$ARGUMENTS 承接現象描述
3. sdd-done.md — 對應範本 6-A，$ARGUMENTS 承接計畫檔名

建立後示範每個指令的呼叫方式給我看。
⚠️ 若 slash command 的檔案格式與目前版本不符，以官方文件為準調整。
```

## 🔸 8. 下階段建議（適合納入 SDD 但先不做）

1. **重構流程**：行為不變的重構最容易偷偷改壞行為，值得有專屬範本——Spec 段改為「不變式清單」（哪些行為保證不變）＋重構前後的驗收對照。功能二開發前若要整理功能一的程式碼，再納入。
2. **上架前 Release Checklist**：`/sdd-release`——核對 manifest 權限 vs 實際使用、隱私欄位申報內容、版本號、zip 打包。第一次上架前建立。
3. **ADR（架構決策紀錄）**：`docs/adr/` 記錄「為什麼這樣選」（如：為何無後端、為何字幕邏輯隔離成 provider 模組）。目前 REQUIREMENTS.md 0-A 已部分承擔，等決策多了再拆。
4. **定期脫鉤稽核排程**：每完成 3~5 個功能跑一次 6-B，比壞了才修便宜。
